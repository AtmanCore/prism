# Safety

**Nothing is posted to GitHub unless you explicitly confirm it.** This page explains what stops it, and where the limits are.

- **Background reviews are blocked from writing.** `claude -p` runs with an allow-list (`Bash`, `Read`, `Grep`, `Glob`, `Agent`, plus your `tickets.read_tools`) and a deny-list: `gh pr comment/review/edit/merge/close/create`, `gh api`, `gh issue` writes, `gh repo`, `gh project`, `gh alias`, `gh auth`, `bash -c`, `git push` (and `git -C …`/`git -c …`), `curl`, `wget`, `kubectl`, `docker`, `gcloud`, `aws`, file edits, and your `tickets.deny_tools`. The deny-list matches command prefixes, so it's a strong guard rail rather than a sandbox.
- **What the token itself allows still matters.** Reviews hold the same GitHub token as the UI. A classic token with the `repo` scope (the one [setup.md](setup.md#2-github-one-token) recommends) can also push and merge, so the deny-list is what stops a review from doing that. A review that slips past it (for example with a `python3 -c` script), or the PR's own lint code (see Trust boundary), could use whatever the token allows. For a stricter setup, use a fine-grained token: without *Contents: write* it can't push code or merge, whatever command runs; with *Pull requests: write* (so the Post button works) a review could still comment on, approve, close or edit PRs. **In Docker**, a fine-grained *Pull requests: Read* token (if you never post or approve from PRism) means reviews can't write to GitHub at all. **Natively**, reviews also run as you, with your `gh` keyring login and SSH keys, so the deny-list is the only guard; use Docker if that matters.
- **Posting and approving need your typed confirmation** (`comment` / `approve`) in the UI and an explicit flag on the server. Nothing else writes to GitHub (the Approve permission check is a no-op request, see [Approving](usage.md#posting-comments-opt-in)).
- **Reviewed repos can't configure Claude.** Reviews use `--setting-sources user`, so a PR's own `.claude/settings.json` (hooks, permissions), `.mcp.json` and `CLAUDE.md` are ignored. Your own `~/.claude` settings, hooks and `CLAUDE.md` still apply to reviews.
- **Trust boundary:** the code pass runs the repo's own lint tooling (`make lint`, `npm run lint`, …) in the worktree, and that executes code from the PR. Anything the PR runs can read every token in `.env` (GitHub, Claude, Atlassian). Use this on repos whose contributors you trust (your org's PRs). PRs from forks are listed but only reviewed when you click **Review** (`github.auto_review_forks` changes that).
- **Local only:** the server binds to `127.0.0.1`, answers only requests addressed to `localhost`/`127.0.0.1` (which blocks DNS-rebinding pages), and POST endpoints reject cross-site requests. The knowledge-base folder picker can only see inside your home folder.
- **Reviews only read knowledge bases.** Secrets are never resolved and no service is started. The exceptions are ones you set up: a KB's `refresh_command` runs before reviews, and **Refresh now** on a skill-built KB lets Claude write inside that KB only (no shell, no MCP servers, no network tools).

To report a security issue, see [SECURITY.md](../SECURITY.md).
